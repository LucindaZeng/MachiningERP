# 工厂 ERP 及上下游协同门户 — 安全需求规格说明书

| 项目 | 内容 |
|---|---|
| 文档版本 | v1.0 |
| 适用系统 | 工厂 ERP 核心系统 + 上下游协同门户（供应商 / 客户） |
| 部署形态 | 公网开放，多租户（外部合作方）+ 内部员工 |
| 文档性质 | 开发强制要求，纳入验收标准 |

---

## 0. 文档使用说明

### 0.1 需求编号规则

`SEC-<模块>-<序号>`，例如 `SEC-AUTHZ-003`。编号一经分配不得复用，废弃需求标记为 `[已废弃]` 保留。

### 0.2 优先级定义

| 级别 | 含义 | 处理方式 |
|---|---|---|
| **P0** | 强制要求 | 未实现则不允许上线，验收一票否决 |
| **P1** | 应当实现 | 上线前必须实现，如需延期须书面记录风险并指定负责人与截止日期 |
| **P2** | 建议实现 | 纳入后续迭代计划 |

### 0.3 术语

- **核心系统**：ERP 主体，承载生产、库存、财务、采购、销售全量数据
- **协同门户**：面向外部供应商 / 客户的独立系统
- **租户（Partner）**：一个外部合作单位，是数据隔离的基本边界
- **主体（Principal）**：一次请求的操作者身份，含内部员工与外部用户

### 0.4 威胁模型（本文档的假设前提）

| 编号 | 威胁来源 | 典型场景 | 主要防护章节 |
|---|---|---|---|
| T1 | 互联网匿名攻击者 | 漏洞扫描、SQL 注入、暴力破解、DDoS | 2、6、9 |
| T2 | 合法外部用户越权 | 供应商 A 查看供应商 B 的订单与价格 | 4 |
| T3 | 外部合作方账号被盗 | 对接人电脑中木马，凭据泄露 | 3 |
| T4 | 内部员工滥用 | 离职前批量导出客户与成本数据 | 4、5、12 |
| T5 | 供应链攻击 | 第三方依赖库植入后门 | 16 |
| T6 | 勒索软件 | 服务器被加密，生产停摆 | 14、15 |
| T7 | 运维权限失控 | 离职运维仍持有服务器与数据库权限 | 15 |

**设计原则**：默认拒绝（Default Deny）、最小权限（Least Privilege）、纵深防御（Defense in Depth）、失败安全（Fail Secure）。任何异常情况下系统应拒绝访问而非放行。

## 1. 系统架构安全要求（ARCH）

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-ARCH-001 | 协同门户与 ERP 核心系统必须为**独立部署的两套服务**，使用独立进程、独立域名、独立应用服务器 | P0 |
| SEC-ARCH-002 | 协同门户**不得直连 ERP 核心数据库**，只能通过受控的内部 API 获取数据 | P0 |
| SEC-ARCH-003 | ERP 核心系统**不得在公网开放任何端口**，仅监听内网地址 | P0 |
| SEC-ARCH-004 | 内部 API 必须实施白名单：仅暴露门户功能所必需的接口，逐个登记在《对外接口清单》中，未登记接口默认不可调用 | P0 |
| SEC-ARCH-005 | 门户与核心之间的调用必须双向鉴权（mTLS 或签名令牌），核心系统需校验调用方身份 | P1 |
| SEC-ARCH-006 | 数据库、缓存（Redis）、消息队列、对象存储**一律不得暴露公网**，仅允许应用服务器内网访问 | P0 |
| SEC-ARCH-007 | 生产、测试、开发环境必须物理或网络隔离，**测试环境严禁使用生产真实数据**；如必须使用，须先脱敏 | P0 |
| SEC-ARCH-008 | 网络分区至少划分为：DMZ（门户、WAF）、应用区（ERP 核心）、数据区（DB、存储）、管理区（堡垒机）。各区之间默认拒绝，按需开放端口 | P1 |

**架构参考图**

```
Internet
   │
   ├── 员工 ──────► 零信任/VPN ─────────────┐
   │                                        │
   └── 供应商/客户 ─► WAF/CDN ─► 协同门户   │
                                  │ (DMZ)   │
                                  ▼         ▼
                            内部 API 网关（白名单 + 鉴权）
                                        │
                                        ▼
                                  ERP 核心（应用区）
                                        │
                                        ▼
                            DB / Redis / 对象存储（数据区）
```

## 2. 网络与接入层（NET）

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-NET-001 | 所有公网入口必须经过 WAF，WAF 需开启 SQL 注入、XSS、命令注入、路径穿越、反序列化、扫描器识别规则 | P0 |
| SEC-NET-002 | **源站隐藏**：源站安全组只放行 WAF 回源 IP 段；同时在 Nginx 层校验 WAF 注入的回源鉴权 Header，缺失则拒绝 | P0 |
| SEC-NET-003 | 全站强制 HTTPS，HTTP 请求 301 跳转至 HTTPS | P0 |
| SEC-NET-004 | 仅启用 TLS 1.2 及以上，禁用 TLS 1.0/1.1、SSLv3、RC4、3DES、NULL 及导出级密码套件 | P0 |
| SEC-NET-005 | 启用 HSTS：`Strict-Transport-Security: max-age=31536000; includeSubDomains` | P1 |
| SEC-NET-006 | 管理后台使用**独立域名或独立路径 + IP 白名单**，不与外部门户共用入口；WAF 管理面板端口同样限制来源 IP | P0 |
| SEC-NET-007 | 员工访问 ERP 核心必须经由 VPN 或零信任网关，不得通过公网直接访问 | P0 |
| SEC-NET-008 | 部署 DDoS 防护，至少启用云厂商基础防护；对协同门户设置连接数与新建连接速率上限 | P1 |
| SEC-NET-009 | SSH 端口不对公网开放，运维访问统一经堡垒机；如必须开放，须改非标端口 + 密钥登录 + IP 白名单，禁用密码登录与 root 直登 | P0 |
| SEC-NET-010 | 服务器对外开放端口须登记造册，每季度复核一次，未登记端口一律关闭 | P1 |

**安全响应头（P1，全部必须设置）**

```
Content-Security-Policy: default-src 'self'; frame-ancestors 'none'; object-src 'none'
X-Content-Type-Options: nosniff
X-Frame-Options: DENY
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: geolocation=(), microphone=(), camera=()
```

## 3. 身份认证（AUTH）

### 3.1 账号开通与生命周期

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-AUTH-001 | **禁止外部用户自助注册**。所有外部账号由内部业务人员在后台创建，采用邀请制（发送一次性激活链接，有效期 ≤ 48 小时） | P0 |
| SEC-AUTH-002 | 每个外部账号必须绑定唯一的租户（Partner），且**绑定关系创建后不可修改**，如需变更须停用后重建 | P0 |
| SEC-AUTH-003 | 系统必须提供账号状态字段：`待激活 / 正常 / 锁定 / 停用`，停用账号立即失效且现有会话强制下线 | P0 |
| SEC-AUTH-004 | 合作关系终止或对接人变更时，业务人员须在系统内停用账号；系统提供批量停用某租户全部账号的功能 | P0 |
| SEC-AUTH-005 | 系统须支持**账号有效期**设置，到期自动停用；外部账号默认有效期不超过 12 个月，到期前 30 天提醒续期 | P1 |
| SEC-AUTH-006 | 系统须自动生成《休眠账号报表》：连续 90 天未登录的账号列表，推送至管理员每月复核 | P1 |
| SEC-AUTH-007 | 内部员工离职流程须包含 ERP 账号停用节点，与 HR 系统联动或提供人工核对清单 | P1 |

### 3.2 口令要求

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-AUTH-010 | 口令最小长度 12 位，须包含大写、小写、数字、符号中的至少三类 | P0 |
| SEC-AUTH-011 | 口令必须使用 **bcrypt（cost ≥ 12）或 Argon2id（m=19456KB, t=2, p=1）** 加盐哈希存储；**严禁**明文、MD5、SHA1、无盐 SHA256 | P0 |
| SEC-AUTH-012 | 禁止使用弱口令，须校验常见弱口令字典（至少覆盖 Top 10000）及与用户名、公司名、手机号的相似性 | P1 |
| SEC-AUTH-013 | 初始口令必须随机生成且首次登录强制修改；不得使用统一初始口令 | P0 |
| SEC-AUTH-014 | 口令重置须通过绑定手机或邮箱验证，重置链接一次性使用、有效期 ≤ 30 分钟；重置成功后强制下线全部会话 | P0 |
| SEC-AUTH-015 | 口令找回流程**不得因账号不存在而返回不同提示**，避免账号枚举 | P1 |
| SEC-AUTH-016 | 系统不得提供任何形式的口令明文查看或找回功能 | P0 |
| SEC-AUTH-017 | 口令有效期 90 天（可配置），到期强制修改；新口令不得与前 5 次重复 | P2 |

### 3.3 多因素认证（MFA）

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-AUTH-020 | 以下角色**强制启用 MFA**：系统管理员、财务、采购、销售主管、全部外部账号 | P0 |
| SEC-AUTH-021 | MFA 采用 TOTP（RFC 6238，30 秒周期，6 位）或短信验证码；TOTP 为首选 | P0 |
| SEC-AUTH-022 | MFA 密钥须加密存储；提供一次性恢复码（10 个，使用即失效），恢复码同样哈希存储 | P1 |
| SEC-AUTH-023 | 管理员不得代替用户解绑 MFA；如需解绑须走工单流程并留存审批记录 | P1 |
| SEC-AUTH-024 | 敏感操作（修改银行账号、批量导出、权限变更）须二次验证（重新输入口令或 MFA） | P0 |

### 3.4 登录防护

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-AUTH-030 | 同一账号连续登录失败 5 次，锁定 15 分钟；再次失败锁定时间翻倍，上限 24 小时 | P0 |
| SEC-AUTH-031 | 同一 IP 在 10 分钟内针对不同账号失败超过 20 次，临时封禁该 IP | P0 |
| SEC-AUTH-032 | 登录失败提示统一为「用户名或密码错误」，**不得区分账号不存在与密码错误** | P0 |
| SEC-AUTH-033 | 连续失败 3 次后启用图形验证码或人机验证 | P1 |
| SEC-AUTH-034 | 记录并展示「上次登录时间 / IP / 设备」，供用户自查 | P1 |
| SEC-AUTH-035 | 异常登录告警：异地登录、非常用设备、非工作时段（22:00–06:00）登录，须向账号绑定手机或邮箱发送提醒，并记入告警日志 | P1 |

## 4. 授权与多租户隔离（AUTHZ）— **本系统最高风险区**

### 4.1 强制隔离机制

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-AUTHZ-001 | 租户隔离**不得依赖各接口自行编写过滤条件**。必须在数据访问层实施统一强制过滤：ORM 全局过滤器、或数据库行级安全策略（如 PostgreSQL RLS） | P0 |
| SEC-AUTHZ-002 | 所有涉及租户数据的表必须包含 `partner_id` 字段并建立索引，且设为非空约束 | P0 |
| SEC-AUTHZ-003 | 请求上下文中的 `partner_id` **必须从服务端会话推导**，严禁从请求参数、Header、Cookie 中读取 | P0 |
| SEC-AUTHZ-004 | 如确需绕过全局过滤（如内部统计任务），必须调用显式命名的方法（如 `withoutTenantScope()`），且该方法调用点须在代码评审中逐一确认并记录 | P0 |
| SEC-AUTHZ-005 | 单元测试须覆盖：以租户 A 身份查询租户 B 的资源必须返回 404 或 403。该测试为 CI 强制门禁，失败则阻断合并 | P0 |

### 4.2 权限模型

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-AUTHZ-010 | 采用 RBAC 模型，权限粒度至少细化到「功能点 + 操作类型（查/增/改/删/导出/审批）」 | P0 |
| SEC-AUTHZ-011 | 权限校验必须在**服务端每个接口**执行。前端隐藏按钮不构成权限控制 | P0 |
| SEC-AUTHZ-012 | 未显式授权的功能默认拒绝；新增接口默认无人可访问，须显式配置权限点 | P0 |
| SEC-AUTHZ-013 | 内部员工权限须按岗位最小化配置：车间人员不得访问成本与财务数据，采购不得查看销售报价 | P0 |
| SEC-AUTHZ-014 | 权限变更须记录操作人、时间、变更前后内容，并支持导出审计 | P0 |
| SEC-AUTHZ-015 | 禁止存在「超级管理员绕过一切校验」的硬编码逻辑；管理员操作同样记录审计日志 | P1 |
| SEC-AUTHZ-016 | 数据行级权限（如仅可见本部门单据）须在服务端实现，不得由前端传参控制范围 | P1 |

### 4.3 标识符与遍历防护

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-AUTHZ-020 | 对外暴露的资源标识符（订单、附件、单据）**必须使用 UUID v4/v7 或不可预测的雪花变体**，不得使用自增整数 | P0 |
| SEC-AUTHZ-021 | 若因历史原因必须暴露自增 ID，须额外校验该 ID 归属当前租户，且做接口级限流 | P0 |
| SEC-AUTHZ-022 | 越权时统一返回 404（资源不存在），避免通过 403 与 404 的差异探测资源存在性 | P1 |
| SEC-AUTHZ-023 | 批量接口（如按 ID 列表查询）须对列表中**每一个** ID 逐一校验归属 | P0 |

## 5. 数据安全与最小化（DATA）

### 5.1 敏感度分级

| 级别 | 定义 | 示例字段 | 外部门户可见性 |
|---|---|---|---|
| L1 公开 | 可对外公布 | 公司名称、产品型号 | 可见 |
| L2 内部 | 限本单位知悉 | 订单号、交期、数量、物流状态 | 仅本租户可见 |
| L3 敏感 | 泄露造成损失 | 联系人手机、地址、银行账号、合同金额 | 脱敏或仅本租户可见 |
| L4 核心机密 | 泄露造成重大损失 | 成本价、毛利、BOM 明细、配方工艺、其他供应商报价、客户名单全量 | **绝不出现在门户任何接口响应中** |

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-DATA-001 | 门户 API 响应必须采用**白名单字段序列化**（显式声明返回字段），严禁直接序列化数据库实体对象 | P0 |
| SEC-DATA-002 | L4 级字段不得进入门户服务的内存与日志。内部 API 在返回给门户前即完成裁剪 | P0 |
| SEC-DATA-003 | 前端不得依靠 CSS 隐藏或 JS 过滤来「屏蔽」敏感字段——后端不返回才算屏蔽 | P0 |
| SEC-DATA-004 | 展示类接口对 L3 字段默认脱敏：手机号 `138****8000`、银行账号仅显示后 4 位、身份证 `110***********1234` | P1 |
| SEC-DATA-005 | 完整明文查看须单独授权、二次验证，并记录审计日志（谁、何时、查看了谁的什么字段） | P1 |
| SEC-DATA-006 | 单据编号规则不得可推测出经营规模（如全局连续自增），建议采用「日期 + 随机段」 | P2 |

### 5.2 存储与传输加密

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-DATA-010 | L3/L4 字段在数据库中须加密存储（AES-256-GCM），密钥不得与数据同库存放 | P1 |
| SEC-DATA-011 | 数据库磁盘启用透明加密或全盘加密 | P1 |
| SEC-DATA-012 | 应用与数据库之间的连接启用 TLS | P1 |
| SEC-DATA-013 | 备份文件必须加密，加密密钥独立保管 | P0 |

### 5.3 数据导出与批量访问控制

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-DATA-020 | 导出功能须单独授权，非授权角色不可见亦不可调用 | P0 |
| SEC-DATA-021 | 单次导出行数上限可配置（建议内部 10000 行、外部 1000 行），超限须审批 | P1 |
| SEC-DATA-022 | 导出操作必须记录审计日志，含操作人、时间、导出范围、行数、字段清单、结果文件哈希 | P0 |
| SEC-DATA-023 | 导出频率限流：同一账号每小时不超过 10 次；超阈值触发告警 | P1 |
| SEC-DATA-024 | 导出文件建议加水印（操作人工号 + 时间），便于泄露溯源 | P2 |

## 6. 输入校验与 Web 漏洞防护（INPUT）

| 编号 | 要求 | 优先级 |
|---|---|---|
| SEC-INPUT-001 | 所有数据库操作必须使用**参数化查询 / 预编译语句**。严禁字符串拼接 SQL，包括 ORDER BY、LIMIT、表名等动态部分（这些须用白名单映射） | P0 |
| SEC-INPUT-002 | 所有外部输入须在服务端校验：类型、长度、格式、范围、枚举值。采用白名单校验而非黑名单过滤 | P0 |
| SEC-INPUT-003 | 输出到 HTML 上下文须按上下文转义（HTML body、属性、JS、URL 分别处理）；富文本必须经服务端 HTML 净化库过滤 | P0 |
| SEC-INPUT-004 | 严禁将用户输入拼入系统命令、`eval`、动态 SQL、模板引擎的可执行上下文 | P0 |
| SEC-INPUT-005 | 禁止对不可信数据执行反序列化；如必须，须限定允许的类白名单 | P0 |
| SEC-INPUT-006 | 所有涉及状态变更的请求（POST/PUT/DELETE）须校验 CSRF Token，或强制 `SameSite=Strict/Lax` Cookie + Origin 校验 | P0 |
| SEC-INPUT-007 | 服务端发起的外部请求（如回调、图片抓取）须实施 SSRF 防护：URL 白名单、禁止内网网段与 169.254.169.254、禁止重定向跟随 | P0 |
| SEC-INPUT-008 | 文件路径参数须规范化后校验，禁止 `../` 穿越；一律不接受用户传入的绝对路径 | P0 |
| SEC-INPUT-009 | XML 解析须禁用外部实体（XXE 防护） | P0 |
| SEC-INPUT-010 | 前端校验仅作用户体验用途，**不得作为安全边界**，服务端必须重复校验 | P0 |
| SEC-INPUT-011 | 业务逻辑校验须在服务端完成：价格、数量、折扣、金额不得由前端传入决定；订单状态流转须校验前置状态合法性 | P0 |
| SEC-INPUT-012 | 关键写操作须防重放：幂等键或一次性 Token | P1 |

## 7. 文件上传与下载（FILE）

| 编号 | 要求 | 优先级 |
|---|---|---|

| 参数篡改 | 请求体中附加 `partner_id`、`role`、`price` 等参数 | 服务端忽略，以会话与数据库为准 |
| 未认证访问 | 清除 Cookie 后直接请求业务接口 | 返回 401 |
| 会话失效 | 登出后重放原会话请求 | 返回 401 |
